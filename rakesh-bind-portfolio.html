What I actually do

I sit between the business problem and the architecture.

Most AI projects don't fail on the model. They fail on a fuzzy problem, data nobody trusts, or a workflow that ignores how people really work. My job is to close those three gaps before a single agent gets written — then stay close enough to engineering to make the design real.

01

Frame the problem properly

Discovery with the people doing the work, then a written definition: what we're building, for whom, what counts as good, and what we're deliberately not doing yet.

02

Design the AI solution

Model and pattern selection, agent responsibilities, retrieval strategy, guardrails, typed hand-offs, and the quality-versus-latency-versus-cost trade-offs written down rather than discovered in production.

03

Ship it and prove it

Backlog, sprints, UAT and launch with AI, web, data engineering and BI teams — plus evaluation and observability, so the thing that shipped can be measured instead of defended.

A view I keep coming back to

Automate the mechanical middle. Leave the judgement with people. Make both auditable.

The middle is where the hours go

Finding the right log, stitching a trace to a commit, reconciling two spreadsheets. Nobody's judgement is being exercised there, and that's exactly the work worth handing to a system.

Autonomy needs a boundary

Typed schemas, fail-closed pipelines, independent review, token circuit breakers. Guardrails aren't an afterthought — they're what makes the autonomy shippable at all.

If you can't see it, you don't own it

Every product I build ends with a screen showing what the system did, why, what it changed and what it cost. That's what turns an AI feature into something a business can actually rely on.

How I think about AI products

Four things I'd argue for in any room.

Use the model for what it's good at

LLMs are excellent at recall and drafting, unreliable at precise, auditable judgement. Wherever a decision has to be defensible, the LLM proposes and a deterministic system decides. That single split has saved more projects than any prompt I've written.

Guardrails are a feature, not friction

Typed hand-offs, fail-closed pipelines, independent review, token circuit breakers, noise filters. These are what let a business extend autonomy further next quarter instead of switching the system off after the first bad week.

Evaluation before scale

Groundedness, retrieval quality, tool-call correctness, latency and cost per outcome. If there's no way to tell whether version two is better than version one, a roadmap is just a wishlist.

Ship the observability with the feature

A screen that shows what the system did, why, what it changed and what it cost. It's how people learn to trust an AI product, and how a product owner learns where it's actually failing.

At a glance

An engineer's first draft, written by the platform.

When a production service throws an error, this platform does more than raise an alert. It reads the logs, finds the responsible code, writes a fix, has a second AI check it, and opens a pull request for an engineer to review.

The client runs a digital platform for healthcare media and HCP engagement, built from many microservices. Those services need to stay dependable, and the engineers who look after them were spending too much time on repetitive diagnosis. The goal was to give them that time back without giving up control over what reaches production.

01

Shared tracing

One library stamps every log line in every service with a trace ID, so any incident can be followed end to end.

02

Remediation swarm

Five specialised AI agents move from alert to pull request, with safety checks between each step.

03

Observability dashboard

A single screen shows what the AI did, why, what it changed and what it cost.

The challenge

The slow part of an outage is the middle.

A modern microservice estate produces thousands of log lines a minute. When something breaks, an on-call engineer has to notice the alert, find the right logs, reconstruct the failing request, locate the responsible file and commit, write and test a fix, get it reviewed and ship it. The middle steps are mechanical, and they are where most of the hours go.

Context is scattered

Logs, source code and deployment state live in three different systems. Someone has to stitch a trace ID to a file to a commit by hand.

Tools only report

Traditional dashboards show that something broke, not why, and they never propose a fix.

The same bugs come back

Null checks, type mismatches and timeouts get re-diagnosed from scratch by whoever is on call that week.

The approach

Instrument once. Let agents do the mechanical work. Keep people in charge of the decision.

Make every incident traceable

A standard tracing library across all services means an agent can always start from one ID and find everything related to a failure.

Split the work across specialists

Triage, code retrieval, fix writing, review and Git operations are separate agents with strict, typed hand-offs, each easy to test and improve.

End at a pull request

The output is a reviewed proposal in the tool engineers already use. The AI is a teammate that prepares work, and a person merges it.

Instrumentation

Every Node and Python service imports the shared library. It needs no call-site changes and adds a W3C-standard trace ID to logs the service already writes.

Ingestion

Cloud Logging is the system of record. A log-based alert on ERROR severity publishes to Pub/Sub, which pushes to the swarm's webhook.

Remediation

A FastAPI service on Cloud Run accepts the alert, replies instantly, and runs the five-agent workflow in the background.

Insight

A Next.js dashboard turns the swarm's log trail into KPIs, an incident table and a per-incident timeline.

One incident, start to finish

From a stack trace to a pull request.

Scroll through a typical incident. Each step lights up as you reach it.

  1. A service fails

    A payments-related service throws a division-by-zero error. The shared logger stamps the error line with a trace ID.

  2. The alert fires

    Cloud Logging's alert publishes to Pub/Sub, which pushes to the webhook. The webhook answers immediately and starts the swarm in the background.

  3. The Log Analyst triages

    It reads five minutes of logs either side of the error, rates the incident high criticality under the payments rule, and identifies the file at the commit that was running.

  4. The Environment agent fetches the code

    It pulls that exact file from Bitbucket at that commit.

  5. The Coder writes the fix

    It adds a defensive check around the division and explains the change in one sentence.

  6. The Reviewer checks it

    It looks for regressions and security issues, and returns APPROVED.

  7. GitOps opens the pull request

    It creates a branch, commits the patch and opens a PR describing the root cause.

  8. A person takes over

    The dashboard shows all five steps, the before-and-after diff, the PR link and the token spend. An engineer reviews and merges.

The five agents

Specialists with one job each.

Each agent reads defined inputs and must return a strict, typed result. The next agent only runs if the previous one succeeded.

1

Log Analyst

Reads five minutes of logs either side of the error, names the service, file and commit, and rates business criticality as low, medium or high.

Guardrail. A fixed rubric maps error types to criticality. Authentication failures, payment services and database disconnects rank high.

2

Environment Agent

Retrieves the exact source file from Bitbucket at the commit that was actually running in production.

Guardrail. If the logs don't state a commit, it falls back to the currently deployed one.

3

Coder Agent

Writes the corrected file and a short explanation of what changed and why.

Guardrail. It must keep the file's architecture intact and add a comment above the fix.

4

Review Agent

Gives an independent second opinion: no new security issues, valid syntax, and the original bug is actually resolved.

Guardrail. It is a separate persona from the Coder, and only approved work moves forward.

5

GitOps Agent

Creates a branch, commits the fix and opens a pull request that explains the root cause.

Guardrail. It may only use the repository and file the orchestrator supplies. It never invents names.

↻

Orchestrator

Wires the five agents into one workflow, passes state from each to the next, and stops the run the moment a stage fails to report success.

Why it matters. A weak diagnosis can never slide through to code-writing.

Built-in safety controls

Autonomy is only useful if it is bounded.

The first version already included these controls.

Typed hand-offs

Every agent returns a strict schema. A bad generation fails loudly instead of quietly corrupting the next step.

Fail-closed pipeline

If any stage doesn't report success or approval, the workflow stops.

Independent review

A different agent checks the fix before anything reaches Git, so the author of a change is never its only reviewer.

Token circuit breaker

A watchdog counts tokens live for each agent and halts the run at a per-incident limit (30,000 by default). A looping agent cannot run up an open-ended bill.

Noise filter

Events without a trace ID are ignored, so the swarm doesn't react to noise or to its own logs.

Stateless resume

A halted incident can be re-run with a larger budget. The original alert is rebuilt from Cloud Logging by trace ID, so no fragile session state is kept.

Product decisions

Four calls that shaped the product.

A shared library as the foundation

The swarm's first task is to find a trace ID and the logs around it. That only works because every service already emits consistent IDs with no extra developer effort. The library also stamps each line with the deployed commit hash, so the swarm knows exactly which code was running. Treating instrumentation as an internal platform product is what made company-wide automation realistic.

Logs as the system of record

There is no dedicated application database. The swarm's own log lines are the audit trail, and the dashboard is a stateless, read-only view over them. This keeps the swarm cheap and simple to run.

The trade-off: the dashboard reads structured text from logs rather than a typed API. A formal event contract between swarm and dashboard is on the roadmap.

Prove the loop first, then widen the trust

We shipped the full path from log to pull request first, to show the mechanism worked end to end. The guardrails needed to extend that autonomy to more sensitive services were documented as named next steps rather than left implicit.

Keep people in charge of what ships

The pull request is the hand-off. The AI prepares and explains the change, and an engineer decides whether it goes out.

What's next

Extending autonomy responsibly.

  • Alerts to Slack, email or Jira when the AI is stuck or a fix is rejected
  • A confidence signal, so guessed diagnoses go to a person before any code is written
  • A one-click approval screen for pending AI pull requests

Safety rails

  • Small, targeted patches instead of full-file rewrites
  • Automated checks before any PR: syntax, security scan and existing tests
  • A maintained service-to-repository map that stops and asks a person when unsure

Lessons learned

What I'd do again, and differently.

Define a typed contract early

A formal event schema between the swarm and the dashboard would have been sturdier than reading text logs.

Decide risk tiers before wiring Git

Which services may be auto-fixed is a business decision, and it belongs in the design from day one.

Prefer small diffs to full rewrites

Minimal patches are safer, easier to review and can't be truncated.

A production error in. A reviewed pull request out. People in control of what ships.

At a glance

One set of business rules, in one place.

Founded in 1949, the company is one of the most respected independent publishing houses in the country, producing and distributing titles across art, photography, design, comics, lifestyle and young-readers categories for dozens of imprints and partner publishers.

That scale had, over time, buried the reporting platform under four disconnected systems and a mountain of email-and-Excel process. The programme replaced all of it — and the hardest constraint was that every number had to keep matching what the business already knew to be true.

03

Where it started

A decade of accumulated tools, and a business that outgrew them.

Nothing here was a bad decision at the time. Each tool solved the problem in front of it. Together they produced a platform where the same question could be answered four different ways.

Legacy stack

  • Talend ETL — 200+ interconnected, largely undocumented pipelines
  • Snowflake warehouse, with business logic buried in SQL procedures
  • Qlik Sense dashboards, isolated from day-to-day operations
  • Co-op claims, allocations and reconciliations run by hand in Excel, over email
  • User access and permissions managed independently, system by system

Modern platform

  • Cloud-native DAG pipelines on Google Cloud, with validation, logging and retry built in
  • BigQuery as the single enterprise warehouse — one set of business rules
  • Power BI delivered embedded inside one portal, not a standalone tool

One-line pitch

Type a drug name, get a competitor list you can defend.

Sourced from live web search, checked against FDA data, and reconciled with the company's own competitive-intelligence database — with every unverified candidate still visible rather than quietly dropped.

01

Recall from the LLM

Gemini with Google Search grounding proposes plausible competitors from everything on the web. It names candidates; it never decides.

02

Trust from a rubric

An explainable point system scores each candidate against the seed drug's FDA facts. Same rules, same answer, every time.

03

Final say from a person

The analyst adds or removes competitors with one click, and that edit updates the company's ground-truth list live.

The business problem

Knowing who really competes for a patient is a judgment call, not a lookup.

Telling two products genuinely compete — not just that their names sound alike — takes knowing active ingredient, therapeutic class, route, dosage form and regulatory pathway well enough to say so with confidence. Doing that by hand, per product, across a portfolio, doesn't scale.

Manual, inconsistent research

Without a standard process, two analysts researching the same drug can land on two different competitor lists, based on general web research and personal judgement.

Disconnected sources of truth

Authoritative pharmacological facts live in FDA data. The company's own hard-won competitive knowledge lives in a separate internal list. Nothing reconciled the two automatically.

No fast, repeatable entry point

There was no single place to type a drug name and immediately see what the web thinks the competitors are, and whether that matches what the company already has on file.

System architecture

Five parts, one pipeline.

A React single-page app, a Node/Express proxy that handles authentication, a FastAPI backend running the analysis workflow, Gemini for AI-assisted research, and BigQuery as the data layer for both FDA facts and the company's own ground truth.

Ready. Press play to follow one analysis from search box to curated list.

Why there's a proxy in front of the backend

FastAPI sits behind Google Identity-Aware Proxy and only accepts requests carrying a valid, Google-signed token. The React app is a static bundle with nowhere safe to hold credentials, so it never talks to the backend directly — it calls the proxy, which mints a fresh identity token per request and forwards the call with an Authorization header.

The workflow, node by node

An LLM for recall, a rules engine for trust.

The LLM is used for what it's good at: broad recall of plausible competitors from everything on the web. A deterministic scoring engine and a curated internal dataset handle what LLMs are bad at — precise, auditable, regulatory-grade matching. The analyst stays the final arbiter of the ground-truth list.

1

Seed lookup

Looks up the input drug name in the OpenFDA table with a case-insensitive match on brand or generic name.

Guardrail. Nothing found means the workflow stops immediately. There's no analysis without a verified record to compare against.

2

Web search

Calls Gemini with Google Search grounding and a system instruction constraining it to output only a list of drug names.

Guardrail. The response is parsed, de-duplicated and passed on as candidates — nothing more. It has no authority to mark anything as a competitor.

3

Verify & aggregate

Every candidate is checked against the internal list, looked up in OpenFDA, and scored against the seed drug using an explainable point system.

Guardrail. Unverified candidates aren't discarded. The analyst still sees them, flagged.

Matching criterionPointsRationale
Shared UNII (active ingredient identifier)+2Same active substance is the strongest possible signal of direct competition
Shared RxCUI (RxNorm concept ID)+2A standardized clinical-drug identifier match is almost as strong as a UNII match
Shared pharmaceutical class+1Same mechanism-of-action or therapeutic class family
Matching marketing category+1Same regulatory pathway suggests comparable market positioning
Matching route and dosage form (both required)+1Same delivery method matters for patient and prescriber substitution

A candidate needs a score of 2 or more to be labelled verified. Below that it stays in the results as unverified — visible but flagged, never silently discarded.

Useful for prioritising the next iteration, and for setting honest expectations about what the tool does and doesn't guarantee today.

Product · UX

Gemini's competitor-name output is parsed with a hand-written regex over free text rather than a structured JSON response, which is fragile to any change in the model's formatting habits.

Suggested roadmap

Grouped the way a product owner would prioritise it.

Trust and data quality first, then efficiency, then UX polish, then security and operations.

Trust & data quality

  • Structured JSON output from Gemini instead of regex-parsed text
  • Audit log for every add and delete on the competitor list
  • Scheduled refresh of the OpenFDA reference table
  • Revisit the scoring rubric with real analyst feedback

Efficiency & cost

  • Cache analyze results per drug name for a reasonable TTL
  • Basic rate limiting, given each call triggers a paid Gemini request

Product & UX

  • Fix combined-filter logic so a single active filter is respected
  • Finish wiring the accordion view, or remove it
  • Add pagination for drugs with very large competitor sets
  • Surface the verification score itself, not just pass or fail

Security & operations

  • App-level role separation for read versus write access
  • Rename the production table to reflect that it holds production data
  • Tighten CORS if the backend is ever exposed outside the proxy path
